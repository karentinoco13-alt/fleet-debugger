Blueprint: Building and Debugging Connectivity-Dependent Autonomous Vehicles

From the first design decision to a fleet you can debug when it's 300 km away on a weak LTE signal.

This applies to any autonomous Linux/Python vehicle that depends on a network link: drones that live in a base station (drone-in-a-box), ground rovers, inspection robots, uncrewed boats and underwater vehicles, agricultural machines. Where something applies to only one kind of vehicle, it says so.

0. The one rule everything follows from

The vehicle must be safe and useful with zero connectivity. Connectivity adds visibility and control. It is never a dependency for safety.

Everything below falls out of that rule:

If the link is… The vehicle should…
Good Stream live state, upload data, accept commands, take OTA updates
Degraded Send only heartbeats and events; queue everything else
Lost (seconds) Continue the current safe action; keep logging
Lost (minutes) Run its pre-agreed lost-link behavior (return home / hold / return to base station / stop)
Lost (days) Stay safe, keep its black box, recover itself, and backfill when it returns

"Ideal state" for one of these systems therefore means: every vehicle can always answer "am I healthy, and why not?" by itself, records the answer locally, and gets it to a human as soon as any link allows.

The division between layers

Layer Owns Must keep working when…
Flight/motion controller Stabilization, failsafes, geofence The companion computer crashes
Safety system Parachute/FTS/e-stop Everything else has failed
Companion computer Autonomy, payloads, health, logging The network is down
Base station / edge Charging, shelter, weather gating, local cache, multi-link The cloud is down
Cloud Fleet view, history, OTA, alerting, humans A single site is offline

An operations or analytics platform (mission planning, inspections, reports) sits at the top as the operations and data layer: missions, inspections, insights, reports. The system in this repo is the engineering layer under it, answering "why did that mission fail, and what's broken on the vehicle?"

2. Building it: the phases

Phase 1 — Design for debuggability (before writing code)

  1. Run an FMEA. List every failure mode (GPS loss, link loss, brownout, prop damage, lid jam, process crash, disk full, clock drift…), and for each one say how it's detected, what the vehicle does on its own, and what a human needs to see. This repo's rules.py and rootcause.py are that table turned into code.
  2. Choose hardware that recovers itself:
  3. A separate flight controller (MCU/RTOS) from the Linux companion, so a Linux crash ≠ a crash landing.
  4. A hardware watchdog on the companion (/dev/watchdog driven by systemd RuntimeWatchdogSec=).
  5. An independent safety system with its own power and arming logic.
  6. Industrial storage (eMMC/NVMe with power-loss protection, not consumer SD cards).
  7. A dual-SIM modem or two modems on different carriers; an external antenna.
  8. Out-of-band power control at the base station (a cellular-controlled relay or a smart PDU), so you can power-cycle a hung computer remotely.
  9. A GPS-disciplined clock (PPS → chrony). Without consistent time you can't correlate logs across systems.
  10. Define the lost-link behaviors per mission phase and get them signed off (for drones, they also go in the regulatory beyond-visual-line-of-sight safety case).

Phase 2 — The onboard software platform

Concern Ideal approach
OS Immutable, read-only root filesystem with an A/B partition layout (RAUC, Mender, SWUpdate, or OSTree). A bad update boots back to the last good image automatically.
Processes Each component is a systemd unit with Restart=on-failure, WatchdogSec= (the app calls sd_notify("WATCHDOG=1")), MemoryMax=, CPUQuota=. A leaking perception node gets killed and restarted, not the whole box.
Python A pinned virtualenv baked into the image (no pip install in the field); faulthandler enabled; an excepthook that logs structured tracebacks; supervised threads (a dead thread must kill its process so systemd notices).
Middleware ROS 2 / MAVLink router / ZeroMQ; topic rate monitoring (a silent topic is a fault).
Logging Structured (JSON) logs to the journal with persistent storage and a size cap; flight logs (ULog/DataFlash) and rosbags in a rotating ring buffer.
Black box A bounded, fsync'd local spool of health snapshots. It survives reboots and hard landings (uplink.py implements this).
Health agent Read-only, resource-limited, runs on its own regardless of the network (agent.py).
Time chrony with GPS/PPS and NTP; all logs in UTC.
Config Versioned, delivered by the fleet config service, validated before it's applied, recorded in every health report.
Secrets A per-device identity (X.509 cert in a TPM/secure element); no shared passwords.

Phase 3 — Connectivity design

3.1 Assume the network is hostile and intermittent. - Outbound-only. Vehicles connect out to the cloud. Never require an inbound port: carrier CGNAT will block it anyway, and an open port is an attack surface. - Multi-link. Bond or fail over between carriers, 5G, satellite (Starlink/Iridium for heartbeats), and local radio/mesh. Track which link is active in every report. - Encryption and identity everywhere. mTLS or WireGuard, with device certificates you can revoke.

3.2 Tier traffic by priority, not by type

Tier Example Size When it's sent
P0 heartbeat alive, status, GO/NO-GO, position <200 B Every 5–30 s, over any link including satellite/SMS
P1 events new finding, failsafe, mission abort ~1 KB Immediately, retried, queued if offline
P2 summaries compact diagnosis, metrics 1–5 KB Every cycle when the link is good
P3 full state full snapshot, top-N logs 10–100 KB On status change, or every 10 min
P4 bulk flight logs, rosbags, imagery, debug bundles MB–GB Only at the base station / on Wi-Fi / unmetered, resumable uploads

This repo's Uplink implements P1–P3: compact vs. full, store-and-forward, at-least-once delivery.

3.3 Protocols. MQTT 5 (persistent sessions, QoS 1, small overhead) or HTTPS batches (simple, works through any proxy). Avoid chatty request/response protocols over cellular.

3.4 Detect silence as a fault. The cloud must tell "healthy and quiet" apart from "dead". Expected heartbeats that don't arrive → SILENT → automatic NO-GO, an alert, and the last known state shown (console.Fleet.view() does this).

Phase 4 — Cloud / fleet platform

  • Ingest → time-series DB (Timescale/Influx/Prometheus) for metrics, an event store for findings, and object storage for bundles and logs.
  • Rules run in two places. On the vehicle (works offline, decides GO/NO-GO) and in the cloud (fleet-wide correlation: "every vehicle at site X lost GPS at 14:02" means a site-level cause such as jamming, a weather event, or a carrier outage, not a hardware fault).
  • Fleet registry: hardware revision, firmware/software versions, config hash, and maintenance history per vehicle. Most fleet bugs turn out to be "only on hardware rev C with software ≥ 2.4".
  • OTA with staged rollouts: canary 1 vehicle → 5% → 25% → 100%, with automatic halt if health metrics regress; never update a vehicle mid-mission.
  • Alerting: alert on changes in state and on SLO burn, not on every poll (integrations.Notifier).
  • Trends: recurring findings per vehicle/site are the maintenance backlog (history.py).

3. Debugging vehicles you can't reach: the escalation ladder

Use the lowest rung that answers the question. Each rung up costs more bandwidth, risk and human time.

 Rung 0  Passive telemetry      dashboards, heartbeats, findings, trends        (always on)
 Rung 1  Automatic diagnosis    rules + root-cause hypotheses + GO/NO-GO          (always on)
 Rung 2  On-demand pull         service logs, debug bundle, flight logs           (on request)
 Rung 3  Remote shell           just-in-time, audited reverse tunnel              (break-glass)
 Rung 4  Remote remediation     restart service, reboot, clear disk, re-calibrate (approved actions)
 Rung 5  Remote fix             config push, OTA patch, rollback to the A/B slot  (change control)
 Rung 6  Out-of-band recovery   power-cycle via relay, recovery partition, serial (box is unresponsive)
 Rung 7  Truck roll             on-site technician, with the bundle already in hand

Rung 0–1: Know before you ask

Every report carries enough context that most incidents are diagnosed without touching the vehicle: findings with fix instructions, correlated root causes, software/config version, link quality, and the last N error lines. Run this repo's demo to see it.

Rung 2: Pull, don't poke

  • GET /logs?unit=…: allow-listed journal access, no shell needed.
  • GET /bundle: one archive with the diagnosis, journal, dmesg, process list, USB tree, video devices, modem status, pip freeze and flight logs. Attach it to the ticket. Collect once, analyze offline.
  • Flight-log analysis (analyze-log) gives a timeline of what was already going wrong before the failsafe.

Rung 3: Remote shell, done safely

  • Reverse tunnels only: the vehicle dials out (WireGuard/Tailscale/Teleport/AWS SSM/Cloudflare Tunnel). No inbound ports.
  • Just-in-time access: a short-lived certificate issued per session, tied to a ticket, recorded (session recording), with two-person approval for armed or flying vehicles.
  • Never on a flying vehicle unless the procedure requires it; prefer when it is at its base station.
  • Use tmux/mosh so a link drop doesn't kill your session and leave a half-finished command.

Rung 4: Pre-approved remediations

Implemented in actions.py. See "How a remote action flows" below.

A small, typed allow-list of actions (restart_service(name), reboot, clear_cache, trigger_ffc, recalibrate_compass_at_base), each with a precondition (vehicle disarmed and at its base station), a timeout, and an automatic verify step (re-run diagnose). Many teams let the vehicle run these itself for known faults: self-healing that is logged and reported.

How a remote action flows

 operator (logged in) ──► console: POST /api/action {vehicle, action, params, ticket, reason}
                            │ builds envelope {action, params, operator, ts, expires, nonce}
                            │ signs it: HMAC-SHA256 with that vehicle's secret
             ┌──────────────┴───────────────┐
        pull vehicle                   push vehicle (CGNAT)
   POST /actions/run now           queued in the vehicle's mailbox; delivered in the
                                   response to its next uplink POST (no inbound port)
             └──────────────┬───────────────┘
                 vehicle verifies: signature · not expired · nonce unused
                 checks preconditions on LIVE state: disarmed · docked · …
                 runs the action → re-diagnoses → resolved / remaining / new
                 appends to the local audit log → result goes back to the console

Commands expire (5 minutes by default) because a "reboot" queued while a vehicle was offline must not fire hours later, when it may be mid-mission. Unknown state fails the precondition: with no telemetry, the vehicle can't prove it's disarmed, so it refuses.

Rung 5: Fixes over the air

Config pushes and OTA updates follow the staged rollout. The A/B layout means every remote update has a remote undo. The device must confirm the update is healthy (agent says GO) within N minutes, or it rolls back on its own.

Rung 6: When the computer itself is unresponsive

This is where the hardware choices from Phase 1 pay off: - The hardware watchdog reboots a hung kernel automatically. - The base station's out-of-band channel (separate modem + relay/BMC/serial console) lets you power-cycle or reach a console even when the main OS or main link is dead. - A recovery partition boots a minimal image that phones home and accepts a re-flash.

Rung 7: Truck roll, with everything prepared

The technician arrives with the bundle already analyzed, the likely part (prop, charging contacts, GPS cable) in hand, and a checklist generated from the findings. Success measure: one visit, not two.

Debugging techniques that work at a distance

Technique Why it matters remotely
Correlate across layers by timestamp FC log + journal + dmesg + base station log + modem log on one timeline. Most "mysteries" are a power or link event a few seconds earlier (rootcause.py, the preceded_by field in log analysis).
Compare against the fleet "Only this vehicle" → hardware. "Every vehicle at this site" → environment/RF/carrier. "Every vehicle since v2.4" → software.
Replay Pull the flight log/rosbag and replay it through the autonomy stack in SIL to reproduce the decision the vehicle made.
Increase logging remotely, temporarily A config flag that raises verbosity for one subsystem for N hours, then reverts automatically.
Keep snapshots before and after Capture state when a fault starts and when it clears; flapping faults hide in the gap.
Health in the version string Every report includes the software version and config hash, so you can bisect across the fleet.

4. Security (it's a remotely reachable robot)

  • A per-device identity in hardware (TPM/secure element), mTLS, revocable certificates.
  • Signed OTA images, verified boot where the SoC supports it.
  • The health agent is read-only and resource-capped (see deploy/fleetdebug-agent.service); commands go through a separate, authenticated, audited path.
  • Least privilege: the agent runs in the groups it needs (systemd-journal, dialout, video), not as root.
  • Rate-limit and audit every remote action; alert on unusual access.
  • Plan for GNSS spoofing/jamming detection (sudden position jumps, fleet-wide GPS loss at one site).

Arquitectura: cómo construir y depurar vehículos autónomos que dependen de la conectividad

Desde la primera decisión de diseño hasta una flota que se puede depurar aunque esté a 300 km, con una señal LTE débil.

Aplica a cualquier vehículo autónomo con Linux y Python que dependa de un enlace de red: drones que viven en una estación base (drone-in-a-box), robots terrestres, robots de inspección, embarcaciones y vehículos submarinos sin tripulación, y maquinaria agrícola. Cuando algo aplica a un solo tipo de vehículo, se indica.

0. La regla de la que se desprende todo

El vehículo debe ser seguro y útil sin ninguna conectividad. La conectividad agrega visibilidad y control. Nunca es una dependencia para la seguridad.

Todo lo demás se desprende de esa regla:

Si el enlace está… El vehículo debe…
Bien Transmitir su estado, cargar datos, aceptar comandos y recibir actualizaciones OTA
Degradado Enviar solo señales de vida y eventos; poner todo lo demás en cola
Perdido (segundos) Continuar con la acción segura en curso; seguir registrando
Perdido (minutos) Ejecutar el comportamiento acordado ante pérdida de enlace (volver a casa / mantenerse / volver a la estación base / detenerse)
Perdido (días) Mantenerse seguro, conservar su caja negra, recuperarse solo y enviar lo pendiente al volver

Por lo tanto, el "estado ideal" de estos sistemas es: cada vehículo puede responder siempre por sí mismo "¿estoy sano y, si no, por qué?", guarda la respuesta localmente y se la hace llegar a una persona en cuanto cualquier enlace lo permita.

Arriba de todo está una plataforma de operaciones o analítica (planificación de misiones, inspecciones, reportes): es la capa de operaciones y datos. El sistema de este repositorio es la capa de ingeniería debajo de ella, que responde "¿por qué falló esa misión y qué está roto en el vehículo?"

2. Cómo construirlo: las fases

Fase 1: diseñar pensando en la depuración (antes de escribir código)

  1. Haga un AMEF (análisis de modos de falla y efectos). Liste cada modo de falla (pérdida de GPS, pérdida de enlace, caída de voltaje, hélice dañada, tapa trabada, proceso que se cae, disco lleno, reloj desfasado…) y, para cada uno, indique cómo se detecta, qué hace el vehículo por sí solo y qué necesita ver una persona. Los archivos rules.py y rootcause.py de este repositorio son esa tabla convertida en código.
  2. Elija hardware que se recupere solo:
  3. Un controlador de vuelo (MCU/RTOS) separado de la computadora Linux, para que una falla de Linux no sea un aterrizaje forzoso.
  4. Un watchdog de hardware en la computadora a bordo (/dev/watchdog, controlado por RuntimeWatchdogSec= de systemd).
  5. Un sistema de seguridad independiente, con su propia energía y lógica de armado.
  6. Almacenamiento industrial (eMMC/NVMe con protección ante cortes de energía, no tarjetas SD de consumo).
  7. Un módem con doble SIM o dos módems de operadores distintos; una antena externa.
  8. Control de energía independiente en la estación base (un relé controlado por celular o una PDU inteligente), para poder apagar y encender a distancia una computadora colgada.
  9. Un reloj sincronizado por GPS (PPS → chrony). Sin una hora consistente no se pueden correlacionar registros entre sistemas.
  10. Defina el comportamiento ante pérdida de enlace para cada fase de la misión y obtenga su aprobación (en drones, también forma parte del caso de seguridad regulatorio para vuelos más allá de la línea de vista).

Fase 2: la plataforma de software a bordo

Tema Enfoque ideal
Sistema operativo Sistema de archivos raíz inmutable y de solo lectura, con particiones A/B (RAUC, Mender, SWUpdate u OSTree). Una actualización defectuosa vuelve sola a la última imagen buena.
Procesos Cada componente es una unidad systemd con Restart=on-failure, WatchdogSec= (la aplicación llama a sd_notify("WATCHDOG=1")), MemoryMax= y CPUQuota=. Si un nodo de percepción tiene una fuga, se reinicia ese nodo, no todo el equipo.
Python Un entorno virtual con versiones fijas dentro de la imagen (nada de pip install en campo); faulthandler activado; un excepthook que registra los errores de forma estructurada; hilos supervisados (un hilo muerto debe terminar su proceso para que systemd lo note).
Middleware ROS 2 / router MAVLink / ZeroMQ; monitoreo de la frecuencia de los tópicos (un tópico en silencio es una falla).
Registros Registros estructurados (JSON) en el journal con almacenamiento persistente y un límite de tamaño; registros de vuelo (ULog/DataFlash) y rosbags en un búfer circular.
Caja negra Un respaldo local acotado y sincronizado en disco de los reportes de salud. Sobrevive a reinicios y aterrizajes bruscos (lo implementa uplink.py).
Agente de salud De solo lectura, con recursos limitados, funciona por su cuenta sin importar la red (agent.py).
Hora chrony con GPS/PPS y NTP; todos los registros en UTC.
Configuración Versionada, entregada por el servicio de configuración de la flota, validada antes de aplicarse y registrada en cada reporte de salud.
Secretos Una identidad por dispositivo (certificado X.509 en un TPM o elemento seguro); sin contraseñas compartidas.

Fase 3: diseño de la conectividad

3.1 Asuma que la red es hostil e intermitente. - Solo conexiones salientes. Los vehículos se conectan hacia la nube. Nunca exija un puerto de entrada: el CGNAT del operador lo bloqueará de todos modos, y un puerto abierto es una superficie de ataque. - Multienlace. Combine o alterne entre operadores, 5G, satélite (Starlink/Iridium para señales de vida) y radio local o malla. Registre en cada reporte qué enlace está activo. - Cifrado e identidad en todo. mTLS o WireGuard, con certificados por dispositivo que se puedan revocar.

3.2 Clasifique el tráfico por prioridad, no por tipo

Nivel Ejemplo Tamaño Cuándo se envía
P0 señal de vida vivo, estado, GO/NO-GO, posición <200 B Cada 5–30 s, por cualquier enlace, incluso satélite o SMS
P1 eventos hallazgo nuevo, modo seguro, misión cancelada ~1 KB De inmediato, con reintentos, en cola si no hay enlace
P2 resúmenes diagnóstico compacto, métricas 1–5 KB En cada ciclo, cuando el enlace es bueno
P3 estado completo datos completos, registros principales 10–100 KB Cuando cambia el estado, o cada 10 min
P4 volumen registros de vuelo, rosbags, imágenes, paquetes de depuración MB–GB Solo en la estación base / por Wi-Fi / sin costo por datos, con cargas reanudables

El Uplink de este repositorio implementa P1–P3: compacto o completo, guardar y reenviar, entrega al menos una vez.

3.3 Protocolos. MQTT 5 (sesiones persistentes, QoS 1, poca sobrecarga) o lotes HTTPS (simples, funcionan a través de cualquier proxy). Evite protocolos de petición y respuesta muy conversadores sobre la red celular.

3.4 Trate el silencio como una falla. La nube debe distinguir "sano y callado" de "muerto". Si no llegan las señales de vida esperadas → SILENCIOSO → NO-GO automático, una alerta y el último estado conocido en pantalla (lo hace console.Fleet.view()).

Fase 4: la plataforma en la nube y de flota

  • Recepción → base de series de tiempo (Timescale/Influx/Prometheus) para métricas, un almacén de eventos para los hallazgos y almacenamiento de objetos para paquetes y registros.
  • Las reglas corren en dos lugares. En el vehículo (funciona sin conexión y decide GO/NO-GO) y en la nube (correlación de toda la flota: "todos los vehículos del sitio X perdieron el GPS a las 14:02" indica una causa del sitio, como bloqueo de señal, un evento climático o una caída del operador, no una falla de hardware).
  • Registro de la flota: revisión de hardware, versiones de firmware y software, huella de la configuración e historial de mantenimiento de cada vehículo. La mayoría de los errores de una flota terminan siendo "solo en la revisión C del hardware con software ≥ 2.4".
  • OTA con despliegue por etapas: canario en 1 vehículo → 5% → 25% → 100%, con freno automático si empeoran las métricas de salud; nunca actualice un vehículo en plena misión.
  • Alertas: alerte sobre cambios de estado y consumo del margen de error (SLO), no en cada consulta (integrations.Notifier).
  • Tendencias: los hallazgos recurrentes por vehículo o sitio son la lista de mantenimiento pendiente (history.py).

3. Depurar vehículos a los que no se puede llegar: la escalera de escalamiento

Use el escalón más bajo que responda la pregunta. Cada escalón más arriba cuesta más ancho de banda, más riesgo y más tiempo de personas.

 Escalón 0  Telemetría pasiva       paneles, señales de vida, hallazgos, tendencias  (siempre activo)
 Escalón 1  Diagnóstico automático  reglas + causas probables + GO/NO-GO             (siempre activo)
 Escalón 2  Consulta a pedido       registros, paquete de depuración, vuelos         (a pedido)
 Escalón 3  Terminal remota         túnel inverso temporal y auditado                (emergencia)
 Escalón 4  Corrección remota       reiniciar servicio, reiniciar, liberar disco     (acciones aprobadas)
 Escalón 5  Solución remota         nueva config, parche OTA, volver a la ranura A/B (control de cambios)
 Escalón 6  Recuperación independ.  apagar/encender por relé, partición de rescate   (equipo sin respuesta)
 Escalón 7  Visita en sitio         técnico en el lugar, con el paquete ya analizado

Escalones 0–1: saber antes de preguntar

Cada reporte trae suficiente contexto para diagnosticar la mayoría de los incidentes sin tocar el vehículo: hallazgos con instrucciones de solución, causas raíz correlacionadas, versión de software y configuración, calidad del enlace y las últimas líneas de error. Ejecute la demostración (demo) de este repositorio para verlo.

Escalón 2: consultar, no hurgar

  • GET /logs?unit=…: acceso a los registros de unidades autorizadas, sin necesidad de terminal.
  • GET /bundle: un archivo con el diagnóstico, el journal, dmesg, la lista de procesos, el árbol USB, los dispositivos de video, el estado del módem, pip freeze y los registros de vuelo. Adjúntelo al ticket. Se recolecta una vez y se analiza sin conexión.
  • El análisis de registros de vuelo (analyze-log) da una línea de tiempo de lo que ya estaba fallando antes del modo seguro.

Escalón 3: terminal remota, de forma segura

  • Solo túneles inversos: el vehículo inicia la conexión (WireGuard/Tailscale/Teleport/AWS SSM/Cloudflare Tunnel). Sin puertos de entrada.
  • Acceso temporal: un certificado de corta duración por sesión, vinculado a un ticket, grabado, y con aprobación de dos personas si el vehículo está armado o en vuelo.
  • Nunca en un vehículo en vuelo, salvo que el procedimiento lo exija; mejor cuando está en su estación base.
  • Use tmux o mosh para que una caída del enlace no cierre la sesión y deje un comando a medias.

Escalón 4: correcciones aprobadas de antemano

Implementado en actions.py. Vea "Cómo fluye una acción remota" abajo.

Una lista corta y definida de acciones permitidas (restart_service(nombre), reboot, clear_cache, trigger_ffc, recalibrate_compass_at_base), cada una con una condición previa (vehículo desarmado y en su estación base), un tiempo máximo y una verificación automática (volver a diagnosticar). Muchos equipos dejan que el vehículo las ejecute por su cuenta ante fallas conocidas: autorreparación que queda registrada y reportada.

Cómo fluye una acción remota

 operador (con sesión) ──► consola: POST /api/action {vehículo, acción, parámetros, ticket, motivo}
                            │ arma el sobre {acción, parámetros, operador, hora, vencimiento, nonce}
                            │ lo firma: HMAC-SHA256 con el secreto de ese vehículo
             ┌──────────────┴───────────────┐
      vehículo de consulta           vehículo de envío (CGNAT)
   POST /actions/run ahora          queda en el buzón del vehículo; se entrega en la
                                    respuesta a su próximo envío (sin puerto de entrada)
             └──────────────┬───────────────┘
                 el vehículo verifica: firma · no vencido · nonce sin usar
                 revisa condiciones en el estado ACTUAL: desarmado · en estación · …
                 ejecuta la acción → vuelve a diagnosticar → resuelto / pendiente / nuevo
                 lo agrega a su registro de auditoría → el resultado vuelve a la consola

Los comandos vencen (a los 5 minutos por defecto), porque un "reiniciar" que quedó en cola mientras el vehículo estaba sin enlace no debe ejecutarse horas después, quizás en plena misión. Un estado desconocido no cumple la condición previa: sin telemetría, el vehículo no puede demostrar que está desarmado, así que se niega.

Escalón 5: soluciones por aire (OTA)

Los cambios de configuración y las actualizaciones OTA siguen el despliegue por etapas. Con las particiones A/B, toda actualización remota se puede deshacer a distancia. El equipo debe confirmar que la actualización está sana (el agente dice GO) dentro de N minutos; si no, vuelve atrás por su cuenta.

Escalón 6: cuando la computadora no responde

Aquí rinden las decisiones de hardware de la fase 1: - El watchdog de hardware reinicia solo un kernel colgado. - El canal independiente de la estación base (módem aparte + relé/BMC/consola serie) permite apagar y encender, o llegar a una consola, aunque el sistema principal o el enlace principal estén caídos. - Una partición de rescate arranca una imagen mínima que se reporta y acepta una reinstalación.

Escalón 7: visita en sitio, con todo preparado

El técnico llega con el paquete ya analizado, la pieza probable (hélice, contactos de carga, cable de GPS) en la mano y una lista de verificación generada a partir de los hallazgos. Medida de éxito: una visita, no dos.

Técnicas de depuración que funcionan a distancia

Técnica Por qué importa a distancia
Correlacionar capas por hora Registro del FC + journal + dmesg + registro de la estación base + registro del módem en una sola línea de tiempo. La mayoría de los "misterios" son un evento de energía o de enlace unos segundos antes (rootcause.py, el campo preceded_by del análisis de registros).
Comparar con la flota "Solo este vehículo" → hardware. "Todos los vehículos de este sitio" → entorno, RF u operador. "Todos los vehículos desde la v2.4" → software.
Reproducir Descargue el registro de vuelo o el rosbag y reprodúzcalo en el sistema de autonomía en SIL para recrear la decisión que tomó el vehículo.
Aumentar los registros a distancia, por un tiempo Un parámetro de configuración que sube el nivel de detalle de un subsistema durante N horas y luego vuelve solo.
Guardar el antes y el después Capture el estado cuando empieza una falla y cuando se resuelve; las fallas intermitentes se esconden en ese intervalo.
La salud lleva la versión Cada reporte incluye la versión de software y la huella de la configuración, para poder aislar el problema en toda la flota.

4. Seguridad (es un robot accesible a distancia)

  • Una identidad por dispositivo en hardware (TPM o elemento seguro), mTLS y certificados revocables.
  • Imágenes OTA firmadas y arranque verificado cuando el SoC lo permite.
  • El agente de salud es de solo lectura y tiene recursos limitados (vea deploy/fleetdebug-agent.service); los comandos pasan por un camino aparte, autenticado y auditado.
  • Mínimo privilegio: el agente corre en los grupos que necesita (systemd-journal, dialout, video), no como root.
  • Limite la frecuencia y audite cada acción remota; alerte ante accesos inusuales.
  • Prevea la detección de suplantación o bloqueo de GNSS (saltos bruscos de posición, pérdida de GPS en toda la flota de un sitio).

When a fleet runs it for real

Data stays with the company

The console runs on the company's own server, and vehicle data goes only to that server. Nothing is sent to the app's author or to any outside service. Uploaded flight logs are checked on that server and not stored.

Operators sign in

When sign-in is turned on, each person has their own username and password. Passwords are stored scrambled, never as plain text. Every remote fix is recorded in the Action log: who ran it, on which vehicle, why, and the result.

Remote fixes are locked down

Only fixes on an approved list can run. There's no way to type in free-form commands. Each command is signed with a secret key that only the vehicle and the console share, expires after a few minutes, and can't be reused. The vehicle checks that it's safe first (for example, landed and docked), then checks again afterwards that the fix worked.

Vehicles check who's asking

A vehicle only answers requests that carry its access key, and the console only accepts reports from vehicles that carry the console's key.

When the connection drops

The vehicle keeps its reports on its own disk and sends them when it reconnects. Nothing is lost, and nothing is sent anywhere else.

Good practice

  • Run the console on a private network or VPN, or behind HTTPS, so sign-ins and data are encrypted on the way.
  • Turn on sign-in and give each operator their own login, so the Action log shows who did what.
  • Use a long, unique secret key for each vehicle, and change it if a vehicle is lost or stolen.

Los operadores inician sesión

Cuando el inicio de sesión está activado, cada persona tiene su propio usuario y contraseña. Las contraseñas se guardan cifradas, nunca como texto simple. Cada solución remota queda en el Registro de acciones: quién la ejecutó, en qué vehículo, por qué y el resultado.
